## 1. Technical Overview

Kabadiwala Connect is designed as a high-reliability, offline-first mobile assistant and digital logistics bridge that connects informal waste collectors (*kabadiwalas*) to authorized, formal e-waste recyclers. 

### Target System Topology

```
+-----------------------------------------------------------------------+
|                         FLUTTER COLLECTOR APP                         |
| (UI Layer, Provider State, Offline SQLite Sync Engine, Camera, GPS)   |
+-----------------------------------------------------------------------+
        |                                                       ^
        | [Online REST / HTTPS API]                             | [Background Sync Queue]
        v                                                       v
+-----------------------------------------------------------------------+
|                    NODE.JS + EXPRESS BACKEND API                      |
| (Auth, Authorization, Lot Pipeline, Matching, ERP/Rate Sync Service)  |
+-----------------------------------------------------------------------+
        |                                                       |
        v                                                       v
+-----------------------------+         +-------------------------------+
|     POSTGRESQL DATABASE     |         |  OBJECT / MEDIA STORAGE (S3)  |
| (Authoritative Store, GIS)  |         | (Compressed Lot Photos, KYC)  |
+-----------------------------+         +-------------------------------+
```

### Component Responsibilities & Boundaries

1. **Flutter Mobile App (Collector App)**
   - **Responsibility:** Provide a responsive, low-latency UI supporting vernacular micro-interactions, camera capture, draft lot management, local rate lookup, and offline handover tracking.
   - **Boundary:** Interacts solely with the local SQLite database when offline, and calls the Node.js API when connectivity is active. Never executes raw SQL against external databases.

2. **Local SQLite Database & Offline Sync Engine**
   - **Responsibility:** Persist draft lots, offline submissions, local transaction logs, cached recycler profiles, and rate snapshots on the mobile device. Queue outbound changes in a transactional Sync Queue.
   - **Boundary:** Runs entirely inside the Flutter process via SQLite/`sqflite` bindings. Manages idempotent HTTP requests to the backend upon reconnection.

3. **Node.js + Express REST API**
   - **Responsibility:** Server-side request routing, authentication verification, business rule validation, state machine enforcement, rate calculations, and transactional DB execution.
   - **Boundary:** Exposes versioned endpoints (`/api/v1/...`) to both the mobile client and recycler dashboards. Interfaces strictly with PostgreSQL and S3-compatible media storage.

4. **PostgreSQL Relational Database (with PostGIS)**
   - **Responsibility:** Serve as the authoritative single source of truth for users, lots, recycler registry data, rate charts, spatial index searches (geofencing/distances), and audit histories.
   - **Boundary:** Accessible only by the Node.js API via standard database connection pooling. Direct client access is strictly prohibited.

5. **Media Storage (Object Store / S3)**
   - **Responsibility:** Store compressed e-waste lot photographs, recycler certification documents, and identity verification media.
   - **Boundary:** Files are uploaded via pre-signed S3 URLs generated by the Node.js API to reduce API server memory pressure.

6. **GPS / Location Service**
   - **Responsibility:** Capture geolocation coordinates during lot creation and recycler discovery searches.
   - **Boundary:** Interfaces with hardware GPS via platform channels; falls back gracefully to manual location selection when hardware GPS is unavailable or disabled.

7. **Recycler Dashboard**
   - **Responsibility:** Web portal for authorized recyclers to review incoming handover requests, update pickup schedules, confirm received weights, and issue digital receipts.
   - **Boundary:** Communicates with the same Node.js REST API using Recycler role credentials.

### Layer Responsibilities & Boundaries

- **`core/`**: Non-domain, framework-level building blocks. Standardizes themes, networking, security, localization, and error handling. Imports zero feature code.

- **`shared/`**: Common UI components (e.g., `ValueSummaryCard`, `HeroCreateLotButton`) used across multiple screens. Keeps visual design consistent.
- **`features/`**: Self-contained business domains. Each feature contains its own screens, widgets, and state controllers (`Provider` or `ChangeNotifier`). Features do not directly import from parallel features unless routed via `AppRoutes`.

## 4. State Management

The application utilizes **Provider (`ChangeNotifier`)** for scalable, zero-overhead state management:

```
                          +------------------------+
                          |   MultiProvider Root   |
                          +------------------------+
                                      |
         +-----------------+----------+----------+-----------------+
         |                 |                     |                 |
+-----------------+ +------------------+ +-----------------+ +-------------------+
|  ThemeProvider  | | LanguageProvider | |   LotProvider   | | RecyclerProvider  |
+-----------------+ +------------------+ +-----------------+ +-------------------+
 (UI Color Scheme)    (Locale / Strings)  (Drafts & Lots)     (Discovery Filters)
```

### State Scopes & Management Strategy

1. **Global State (`MultiProvider` at App Root)**
   - `ThemeProvider`: Controls light/dark mode and high-contrast settings.
   - `LanguageProvider`: Maintains selected `AppLanguage` (`hindi`, `marathi`, `english`) and provides string translation functions.
   - `LotProvider`: Manages active lot list and draft creation state.
   - `RecyclerProvider`: Manages recycler search query, distance filters, and material filters.

2. **Feature & Form State**
   - **Lot Creation Draft State**: Managed centrally inside `LotProvider` (`_draftPhotos`, `_draftMaterialKey`, `_draftQuantity`, `_draftUnit`, `_draftCondition`, `_draftNotes`).
   - **Transient Form Control**: Standard `TextEditingController` instances used within UI widgets for raw numeric inputs.

3. **Lot Draft Survival & Interruption Recovery**
   - **Navigation Survival**: Managed centrally in `LotProvider`. Navigating back and forth across creation wizard steps retains input data.
   - **App Termination / Interruption**: When SQLite is integrated (Phase 2), any active draft will be automatically serialized to a local SQLite `draft_lots` table on every step change. If the app crashes or the system kills the background process, `LotProvider.init()` restores the pending draft seamlessly.

## 9. Offline-First Synchronization Engine

```
               [Collector Creates Lot Offline]
                              │
                              ▼
            ┌──────────────────────────────────┐
            │  1. Insert into local SQLite     │
            │  2. Insert item into SyncQueue   │
            │  3. UI updates instantly         │
            └──────────────────────────────────┘
                              │
                    [Network Monitor Event]
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
       [No Connection]               [Connected to API]
               │                             │
        (Wait for Net)        ┌──────────────────────────────┐
                              │ Process Queue sequentially   │
                              │ POST /api/v1/lots (with Key) │
                              └──────────────────────────────┘
                                             │
                                   ┌─────────┴─────────┐
                                   ▼                   ▼
                               [200 OK]           [5xx / Error]
                                   │                   │
                        ┌──────────────────┐  ┌──────────────────┐
                        │ Mark as 'SYNCED' │  │ Increment Retry  │
                        │ Remove from Queue│  │ Exponential Back │
                        └──────────────────┘  └──────────────────┘
```

### Sync Engine Protocols

1. **Idempotency & Duplicate Prevention:** Every queue item receives an `idempotency_key` generated via client-side UUIDv4 (`payload.id` + `timestamp`). If a network timeout occurs after the backend processes a request, re-transmitting the same idempotency key prevents duplicate lot entries.
2. **Retry Policy & Exponential Backoff:** Failed queue requests retry using a geometric backoff formula:  
   Delay = min(2^retry_count * 2, 300) seconds
3. **Conflict Resolution:** The server is the authoritative clock and state manager. If a lot is updated locally while server state has advanced (e.g., recycler marked lot as `CONFIRMED`), the server responds with a state conflict exception (`409 Conflict`), prompting the mobile client to pull down the authoritative server snapshot.
4. **Data Loss Prevention:** Queue items are never deleted from SQLite until the server returns an explicit `200 OK` or `201 Created` HTTP response code.

## 11. Authentication & Authorization

1. **Authentication:** Phone-number-based One-Time-Password (OTP) flow issuing JSON Web Tokens (JWT) containing standard claims (`sub: user_id`, `role: "COLLECTOR" | "RECYCLER" | "ADMIN"`, `exp: 30 days`).
2. **Secure Token Storage:** Tokens on Flutter are stored using platform-native encrypted vaults (`flutter_secure_storage` utilizing macOS Keychain / Android KeyStore).
3. **Authorization Boundaries:**
   - **Collector Role:** Can read/create only their own lots and handover requests (`collector_id == req.user.id`).
   - **Recycler Role:** Can view only handover requests submitted specifically to their business ID. Cannot view other recyclers' financial transactions.

## 13. Rate System Architecture

The rate system provides transparent pricing for informal collectors.

### System Flow
1. **Mock Service (Current):** `MockRateService` (`lib/features/lots/services/rate_service.dart`) returns fixed demo rates:
   - Copper: ₹720.0 / kg
   - Aluminium: ₹180.0 / kg
   - E-Waste (Electronics): ₹45.0 / kg
   - Other Scrap: ₹25.0 / kg
2. **Target Service:** `ApiRateService` fetches daily authorized market rate sheets from the backend endpoint `/api/v1/rates/today`.
3. **Offline Caching:** Rates are stored locally in SQLite with a `cached_at` timestamp. If the device is offline, the app uses the latest cached rate sheet and alerts the user: *"Rates updated 2 days ago (Offline mode)"*.
4. **Estimated Value Calculation:**
   Estimated Value = Quantity * Material Rate
   *Disclaimer:* Explicitly displayed across UI: *"Estimated value only. Final value determined upon recycler inspection."*

## 14. Photo / Media Architecture

Photos enable accurate material classification and prevent valuation fraud.

1. **Capture Pipeline:** Utilizes device camera or gallery (`image_picker`).
2. **Compression Protocol:** Client-side compression lowers image resolution to a maximum width/height of 1280px with 80% JPEG quality, scaling file sizes down from ~5MB to ~250KB.
3. **Storage Strategy:**
   - **Offline:** Saved to local application sandbox (`/data/user/0/.../app_flutter/lots/`).
   - **Online:** Uploaded directly to Object Storage via pre-signed S3 URLs. Only the public S3 URL reference is saved in PostgreSQL (`lot_photos`).

## 15. GPS & Location Architecture

Location data is used exclusively to calculate distance between collectors and authorized recyclers.

1. **Hardware Integration:** Implemented via `LocationService` wrapping `geolocator`.
2. **Permissions:** Requests standard foreground location permission (`LocationPermission.whileInUse`).
3. **Distance Calculation:**
   - **Client-Side (Local Filtering):** Uses Haversine spherical distance formula.
   - **Server-Side (Target Query):** Leverages PostGIS spatial query:
     ```sql
     SELECT id, name, ST_Distance(location, ST_MakePoint(lng, lat)::geography) / 1000 AS distance_km
     FROM recyclers
     WHERE ST_DWithin(location, ST_MakePoint(lng, lat)::geography, radius_meters);
     ```
4. **Fallback:** If location is disabled by user, the app allows manual pin-code or area entry.

## 16. Recycler Matching Engine

Recycler discovery (`RecyclerService`) connects collectors to the optimal disposal yard.

### Matching Criteria (Deterministic MVP)
1. **Material Match:** `recycler.acceptedMaterials.contains(lot.materialKey)`
2. **Distance Radius:** `recycler.distanceKm <= selectedFilterDistance`
3. **Service Type:** Filter by `pickupAvailable == true` if collector requests pickup.
4. **Authorization Seal:** Only display recyclers with verified `isAuthorized == true`.

## 26. Transaction & Handover State Machine

Handover requests follow a strict, non-reversible state lifecycle:

```
┌─────────────────┐       Recycler Accepts       ┌──────────────────┐
│    REVIEWING    │ ───────────────────────────► │    SCHEDULED     │
└─────────────────┘                              └──────────────────┘
         │                                                │
         │ Recycler Rejects                               │ Pickup Verified
         ▼                                                ▼
┌─────────────────┐                              ┌──────────────────┐
│    CANCELLED    │                              │    CONFIRMED     │
└─────────────────┘                              └──────────────────┘
```

### Valid State Transitions Matrix

| Initial State | Target State | Triggering Actor | Pre-Conditions |
| :--- | :--- | :--- | :--- |
| `CREATED` | `REVIEWING` | Collector | Handover request submitted to recycler |
| `REVIEWING` | `SCHEDULED` | Recycler | Pickup date and time assigned |
| `REVIEWING` | `CANCELLED` | Recycler / Collector | Rejection reason specified |
| `SCHEDULED` | `CONFIRMED` | Recycler | Actual weight & payout verified at yard |
| `CONFIRMED` | *Terminal* | System | Transaction receipt issued & logged |

## 35. Open Technical Decisions

The following technical implementation choices are deliberately flagged for explicit team/stakeholder alignment:

1. **Authentication Provider:** Custom Node.js SMS Gateway (e.g., Twilio/Msg91) vs. Firebase Phone Authentication.
2. **Object Storage Host:** AWS S3 vs. MinIO (Self-hosted for data sovereignty).
3. **Push Notification Service:** Firebase Cloud Messaging (FCM) vs. WebSockets for active handover tracking.
4. **Local Database Library:** `sqflite` (Standard SQL) vs. `Isar` / `Hive` (NoSQL key-value store).
5. **Backend Deployment Target:** Containerized Docker on AWS ECS/EC2 vs. Serverless Node.js functions.
6. **EPR Regulatory Compliance Integration:** Directly pushing transaction ledgers to Central Pollution Control Board (CPCB) portals via REST APIs.
